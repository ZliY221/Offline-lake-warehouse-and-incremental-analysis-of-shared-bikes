# 面试讲解稿与追问准备

## 30 秒版本

我用 PySpark 做了一个可复现的共享单车离线湖仓。项目从显式 Schema 的 Bronze 摄取开始，经过 Silver 质量校验、精确重复与主键冲突分流，再用每日站点快照构建 SCD2 维度。Gold 按行程日期做时态关联，产出日指标、分组 Top 路线和匿名 cohort 留存；日期回填只替换受影响的 Bronze/Silver/日指标/路线分区，并对跨分区主键做写前保护。项目有 21 项测试、6 项跨层门禁和带原始三轮数据的本机基准。

## 3 分钟讲解顺序

1. 先说问题：需要同时保留历史站点属性、处理脏数据与重复投递，并保证回填不会误删其他日期。
2. 再说分层：Bronze 保留来源与摄取日期，Silver 做规则和确定性去重，DIM 保存 SCD2 历史，Gold 做时态关联与聚合。
3. 说两个关键决策：主键冲突全部隔离，不任意保留；SCD2 使用左闭右开区间，避免变化日同时命中两个版本。
4. 说可靠性：批次 ID 由日期与 SHA-256 生成，控制记录有运行状态和尝试次数；回填先校验业务日期，再只覆盖目标 Bronze 分区。
5. 最后给证据：21 项测试、6 项跨层质量检查、非目标分区文件哈希不变，以及 10,000 行三轮基准和原始 JSON。

## 高频追问

### 为什么不直接 `dropDuplicates(["trip_id"])`？

完全相同的重复可以保留一条，但同 ID 不同内容说明主键冲突。任意保留会把不可解释的数据送入指标层，所以项目计算业务字段指纹：精确重复保留一条，冲突记录全部隔离。

### SCD2 为什么用左闭右开区间？

变化日属于新版本，前一版本在该日之前结束。`[valid_from, valid_to)` 让任一业务日期最多命中一个版本，关联条件也更清晰。

### 为什么 Gold 维度关联失败要终止？

内连接会静默丢行并使指标偏小。项目先左关联并统计未命中记录，只要起点或终点缺少当日版本就失败，把问题暴露给质量流程。

### 回填是不是全链路增量？

部分是。Bronze 和 Silver 只替换目标摄取日期分区，Gold 日指标与热门路线只替换目标业务日期分区；测试用 Parquet 文件 SHA-256 证明兄弟分区未重写。Cohort 的首次骑行日可能因历史回填改变，所以当前仍全量重算并在清单中记录 `FULL_DATASET`。为保证局部去重正确，合法 `trip_id` 若跨摄取日期出现会在 Bronze 写入前失败。

### 匿名骑行者键是否来自真实用户？

不是。它只由固定种子和 UUID5 生成，不读取或哈希任何真实个人字段，只用于可重复的 cohort 测试。不能把它描述成真实业务脱敏方案。

### 性能数字能说明什么？

只能说明这台 WSL2 本机、Spark `local[2]`、固定 10,000 行输入下的可复现实验。生成数据和 Spark 启动不计入，Parquet 写入和所有 action 计入；报告保留了三轮原始结果，不能外推为生产 SLA。

## 诚实边界

- 没有生产集群部署、云服务、权限治理和作业调度经验；
- 没有 Delta Lake/Iceberg 的事务表能力，当前存储是 Parquet；
- 回填不是全链路事务：cohort 仍全量重算，各层文件也没有跨作业原子提交；
- 本机性能只能作为实验方法和可复现证据；
- 合成匿名键不等于真实企业的隐私工程方案。

## 现场演示

```powershell
./scripts/run-portfolio-demo.ps1
```

脚本在 `build/portfolio-demo/` 隔离目录中重建 Bronze、Silver、站点 SCD2 和三个 Gold 数据集，执行 6 项质量门禁，并运行全部测试。最终 JSON 摘要出现 `"status": "PASS"` 才算演示成功。
