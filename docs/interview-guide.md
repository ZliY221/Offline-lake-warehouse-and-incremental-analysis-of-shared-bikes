# 面试讲解稿与追问准备

## 30 秒版本

我用 PySpark 做了一个可复现的共享单车离线湖仓。项目从显式 Schema 的 Bronze 摄取开始，经过 Silver 质量校验、精确重复与主键冲突分流，再用每日站点快照构建 SCD2 维度。Gold 按行程日期做时态关联，产出日指标、Top 路线和匿名 cohort 留存；日期回填只替换受影响分区。项目有28项测试、6项跨层门禁、最终物理计划、UI REST 任务指标，以及带重试和断点恢复的五阶段编排证据。

## 3 分钟讲解顺序

1. 先说问题：需要同时保留历史站点属性、处理脏数据与重复投递，并保证回填不会误删其他日期。
2. 再说分层：Bronze 保留来源与摄取日期，Silver 做规则和确定性去重，DIM 保存 SCD2 历史，Gold 做时态关联与聚合。
3. 说两个关键决策：主键冲突全部隔离，不任意保留；SCD2 使用左闭右开区间，避免变化日同时命中两个版本。
4. 说可靠性：批次 ID 由日期与 SHA-256 生成，控制记录有运行状态和尝试次数；回填先校验业务日期，再只覆盖目标 Bronze 分区。
5. 最后给证据：28 项测试、6项跨层质量检查、非目标分区文件哈希不变、10,000 行三轮基准、AQE 最终计划、Stage/Task 指标和真实失败恢复清单。

## 高频追问

### 为什么不直接 `dropDuplicates(["trip_id"])`？

完全相同的重复可以保留一条，但同 ID 不同内容说明主键冲突。任意保留会把不可解释的数据送入指标层，所以项目计算业务字段指纹：精确重复保留一条，冲突记录全部隔离。

### SCD2 为什么用左闭右开区间？

变化日属于新版本，前一版本在该日之前结束。`[valid_from, valid_to)` 让任一业务日期最多命中一个版本，关联条件也更清晰。

### 为什么 Gold 维度关联失败要终止？

内连接会静默丢行并使指标偏小。项目先左关联并统计未命中记录，只要起点或终点缺少当日版本就失败，把问题暴露给质量流程。

### 回填是不是全链路增量？

写入范围是依赖驱动的增量：Bronze 和 Silver 只替换目标摄取日期，日指标与路线只替换目标业务日期；cohort 会合并受影响骑行者改写前后的首次活动日，只替换旧、新 cohort 分区。测试用 Parquet SHA-256 证明无关 Silver/日指标/路线分区未重写，并验证骑行者从第二天 cohort 前移到第一天时两个 cohort 分区都被更新。计算层面 cohort 仍扫描完整 Silver，且没有跨层事务，因此不能扩大成生产级全链路增量。合法 `trip_id` 若跨摄取日期出现会在 Bronze 写入前失败。

### 匿名骑行者键是否来自真实用户？

不是。它只由固定种子和 UUID5 生成，不读取或哈希任何真实个人字段，只用于可重复的 cohort 测试。不能把它描述成真实业务脱敏方案。

### 性能数字能说明什么？

只能说明这台 WSL2 本机、Spark `local[2]`、固定 10,000 行输入下的可复现实验。生成数据和 Spark 启动不计入，Parquet 写入和所有 action 计入；报告保留了三轮原始结果，不能外推为生产 SLA。

### 为什么广播站点维度？如何证明生效？

当维度足够小且能放入执行器内存时，广播它可以避免事实表按 Join Key 参与双侧 Shuffle。项目用同一组聚合做受控对照：禁用自动广播时格式化计划出现 `SortMergeJoin` 和 `Exchange`，显式 `broadcast` 后出现 `BroadcastHashJoin` 与 `BroadcastExchange`，并先核对两边结果完全一致。AQE 对照在 action 后保存 `isFinalPlan=true` 的最终计划，其中出现 `AQEShuffleRead coalesced`。

### 如何证明 AQE 真的处理了数据倾斜？

项目生成 20,000 行事实数据，让 90% 行落在同一个 Join Key，并禁用广播。关闭 AQE 时保存 Sort-Merge 基线；开启 AQE、倾斜 Join 和受控阈值后，最终计划出现 `SortMergeJoin(skew=true)` 以及 `AQEShuffleRead ... skewed`。两边 8 个分组的计数和载荷字符总数完全一致。这只能证明本机合成场景触发了运行时拆分，不能直接推导生产提速比例。

### 你如何使用 Spark UI 指标定位问题？

先按 Job Group 找到目标 Job，再从 Stage 判断 Shuffle 边界、任务数、读写字节和 Spill，最后下钻 Task 比较执行时间、GC 和每个任务的 Shuffle 字节。项目的 50,000 行受控作业保存了 2 个完成 Stage、10 个 Task 和 3,302,403 字节的双向 Shuffle；最繁忙 Stage 的任务耗时差异可能同时受 JVM 预热、本地调度与数据分布影响，所以不会只看一个比值就断言倾斜。

### 作业失败后如何重试和恢复？

编排器先校验 DAG 不缺依赖、无环，再按拓扑顺序执行；每次状态变化都原子写入清单，每次尝试分别记录退出码、日志路径和 SHA-256。受控演示让 Silver 第一次返回 75，第二次重试成功，下游 Gold 只在 Silver 和站点维表都成功后执行。对同一清单恢复时，5个成功任务全部跳过。这个实现证明的是单机进程级语义，不是 Airflow 高可用调度或分布式执行经验。

## 诚实边界

- 没有生产集群部署、云服务、权限治理和作业调度经验；
- 没有 Delta Lake/Iceberg 的事务表能力，当前存储是 Parquet；
- 回填不是全链路事务：cohort 写入是受影响分区级，但计算仍全量扫描，各层文件也没有跨作业原子提交或并发回填保护；
- 本机性能只能作为实验方法和可复现证据；
- 合成匿名键不等于真实企业的隐私工程方案。

## 现场演示

```powershell
./scripts/run-portfolio-demo.ps1
```

脚本在 `build/portfolio-demo/` 隔离目录中重建 Bronze、Silver、站点 SCD2 和三个 Gold 数据集，执行 6 项质量门禁，并运行全部测试。最终 JSON 摘要出现 `"status": "PASS"` 才算演示成功。
